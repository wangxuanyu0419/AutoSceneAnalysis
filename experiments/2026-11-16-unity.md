# First spatial control prototype

Date: 16 November 2026. The room can now be explored and manipulated in a standalone Unity simulation, with an Android phone build for the Renkforce viewer. The useful result is a working target/action and motor-input boundary: external synthetic messages can select the mug, reach, grasp, move it, and release it.

## What the room represents

The reference is the same public COCO image 139 used by the photo baseline. The room is an editable, manually authored approximation of its broad layout. The floor, windows, dining furniture, television, cabinets, fireplace, and vase follow the photo. The training mug, book, tray, command panel, and arm are added experiment elements. The [provenance record](../resources/room-proxy-provenance.json) lists these choices.

The nominal room size is 8.4 × 7.4 × 2.9 Unity metres. These are author estimates. The earlier relative-depth model did not recover those dimensions or the hidden sides of the furniture. This prototype establishes a simulation and a control interface; automatic image-to-room geometry is a separate perception milestone.

There are 11 authored interaction targets. Their IDs stay stable within this simulation. They do not claim that the original camera has persistently tracked the corresponding physical objects.

## What can be controlled

The right arm has a simplified hand and an alternative robot appearance. Its controller uses two arm segments to place the hand at a requested endpoint. Three velocity values move that endpoint in the room's coordinates; hand orientation is fixed, and grasp is binary.

Target choice and action choice remain separate. Selecting the mug does not move the arm. An explicit assisted reach moves toward its grasp point; grasp requires the hand to be nearby. Continuous velocity then moves the held prop, and release restores its physics. Drawer, cupboard, light, and television actions demonstrate other object states. Those discrete actions use symbolic commands rather than detailed contact mechanics.

The same message interface accepts desktop controls, gaze interaction, and the synthetic decoder adapters. It checks the scene version, target, action, timestamp, and sequence number. Velocity expires within 250 ms, is capped at 0.45 m/s, and is limited to the arm's workspace. Pause stays active until an explicit resume.

## Verification

The machine-readable [validation summary](unity-validation.json) records the checked builds and results. Full players, screenshots, phone logs, and event streams remain in ignored local folders.

| Check | Evidence |
| --- | --- |
| Windows standalone simulation | 17 runtime checks, including reach, grasp, held-object motion, velocity expiry, pause, release, drawer movement, advancing frames, and nonblank rendering from a hidden window |
| Windows external adapter | Six checks through the actual `inbox.json` path, including target/action input, contact, release, streamed velocity, and rejected-message inspection |
| Android stereo | APK installed and launched on a Huawei MAR-LX1B, Android 10; an actual app screenshot shows the two lens-distorted eye views |
| Android external adapter | Six checks passed; all 27 synthetic messages accepted, including reach, contact, velocity, release, and reset |

The Android build includes ARMv7 and ARM64 and targets Android 8 or newer with OpenGL ES 3. Only this phone has been tested. Its screen size is handled by the renderer; the viewer's lens geometry still needs the right Cardboard QR profile.

Cardboard's display/input subsystems and gyroscope initialized. The tracked-pose setup follows the pinned SDK's sample, including leaving its generic tracking-state input unbound. The final short test logged 121 distinct head rotations, establishing that sensor-derived pose reaches the camera. A wearer test should confirm looking around, recentering, lens fit, and seated alignment. No physical hand tracking or positional head tracking is supplied by this phone setup.

## Reading the timing evidence

The phone checker estimates application frame cadence by dividing the change in Unity's frame counter by elapsed phone time. This says how frequently the application advanced during the observed interval. It does not measure when a pixel reached the eye after a head movement or neural command. The summary records the observation length alongside the estimate.

The final phone test averaged **38.35 frames per second over 9.05 seconds**. This is a short functional test rather than sustained headset performance. The next performance target is a stable 60 frames per second on this phone, with a longer run and direct delay measurements before assessing motor feedback quality.

The USB adapter estimates the computer-to-phone clock offset from a short clock probe. That makes its synthetic timestamps usable by the prototype's command-age check. A probe round trip is not acquisition-to-display delay and does not synchronize an implanted recording system.

The seven clock probes in the final test had round trips of approximately **54–82 ms**. The phone clock was approximately **0.82 seconds behind the PC**, which the adapter compensated when creating its synthetic messages. Acquisition-to-display delay has not yet been measured.

The earlier approximately 431 ms photo-perception result describes a different loop. A static room map can be prepared before a trial while Unity updates the arm and image continuously. Later moving-object tracking needs its own timing evaluation.

## Reproduce and extend

Use the [quickstart](../docs/unity-quickstart.md) for controls, build paths, hidden execution, and both integration checkers. The Windows player does not need the editor open. The editor itself stayed minimized during the final builds and tests.

The build uses Unity 6000.4.7f1, Universal Render Pipeline 17.4.0, Input System 1.19.0, XR Management 4.5.4, and Cardboard v1.36.0 pinned to `7fb2c0e438d2ef686f51cd59b53da16cc07b1b68`. Package versions and the Git revision are in the repository. The Gradle hook supplies the SDK's Java dependencies following the [official Cardboard quickstart](https://developers.google.com/cardboard/develop/unity/quickstart); the [SDK source and sample](https://github.com/googlevr/cardboard-xr-plugin/tree/7fb2c0e438d2ef686f51cd59b53da16cc07b1b68) establish the phone setup.

For the next experiment, use the mug and tray as a small task with explicit start cues and success regions. Record movement time, endpoint error, path length, failures, and how much assisted reach was used. Replay synthetic velocities with known noise and delay before adding neural replay. Then add the acquisition-compatible transport and clock synchronization. No neural recording or implanted device is connected in this prototype.
